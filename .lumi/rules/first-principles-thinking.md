# 第一性原理思考规范

> 本规范定义了 LibGit2Swift 项目中使用第一性原理（First Principles）进行问题分析和技术决策的指导方针。

---

## 核心原则

**从基本真理出发，通过逻辑推导解决问题，而不是依赖类比、经验或既有结论。**

---

## 1. 思维模式

### 1.1 第一性原理 vs 类比思维

| 场景 | 类比思维（避免） | 第一性原理（推荐） |
|------|-----------------|------------------|
| 技术选型 | "别人都在用这个封装" | "我的问题本质是什么？这个方案如何从根本上解决它？" |
| 性能优化 | "加缓存、升级依赖" | "时间花在哪里？瓶颈是 CPU/IO/网络？" |
| 代码重构 | "按最佳实践重写" | "这段代码的核心职责是什么？当前实现是否偏离？" |
| 解决报错 | "复制粘贴解决方案" | "从数据流、执行流程的基本原理出发定位根源" |

### 1.2 追问本质的方法

遇到问题时，至少问 3 层"为什么"：

```
表面问题：状态查询阻塞主线程

第 1 层：为什么阻塞？→ libgit2 调用是同步的
第 2 层：为什么同步？→ 底层 API 本身没有异步版本
第 3 层：为什么必须在主线程？→ 调用方没有把工作派发到后台
根源：并发调度责任在调用方，而非在封装层
```

## 2. 编码实践

### 2.1 理解底层原理

**不要死记硬背 API，要理解其工作机制。**

```swift
// ❌ 避免：只记住用法
git_index_add_all(index, &options)

// ✅ 推荐：理解 index 的写入语义
// → index 是内存中的暂存区快照，add_all 会重建条目树，
//   大仓库下的成本与条目数相关，这决定了何时该用 add_all、何时逐个 add
```

**libgit2 领域尤其如此**：内存所有权由谁负责、对象是否需要显式 `free`、
哪些调用要求仓库处于特定状态——这些搞错就是崩溃或内存泄漏，
不是"用错了能编译过"的普通错误。

### 2.2 技术决策

**从问题本质出发选择技术方案。**

```
✅ 推荐：基于需求分析
"""
问题本质：
1. 需要线程安全 → libgit2 全局状态是否可重入？
2. 需要取消长耗时操作 → libgit2 提供哪些可中断的入口？
3. 封装层要不要隐藏这些细节？

结论：根据具体问题决定封装边界
"""
```

### 2.3 调试方法

**从基本原理推导问题根源。**

```swift
// 问题：偶发崩溃，堆栈不指向业务代码

// ❌ 避免：盲目试错
// 试试加锁，试试换队列，试试...

// ✅ 推荐：系统分析
"""
1. libgit2 生命周期：initialize/shutdown 是否成对？是否重复调用？
2. 对象所有权：谁在 free？有没有二次释放？
3. 线程模型：多个线程是否同时进入了同一个 repository？
4. 状态前置条件：当前操作是否要求仓库处于某个状态？
"""
```

## 3. 架构设计

### 3.1 从本质推导架构

**设计系统时先问基本问题。**

```
设计一个仓库操作层：

1. 本质是什么？→ 把 libgit2 的 C API 变成安全的 Swift API
2. 核心矛盾是什么？→ 便利性 vs 资源安全（谁负责 free）
3. 基本操作有哪些？→ 打开/关闭、状态、提交、分支、远程
4. 约束条件是什么？→ libgit2 非线程安全；C 指针无 ARC
5. 由此推导：
   - 生命周期：统一用持有者类型管理原始指针
   - 并发：公开 API 串行化，还是要求调用方隔离？
   - 错误：统一错误类型，保留底层错误码
```

### 3.2 简化实现

**找到最简单的正确实现。**

```swift
// ❌ 避免：过度设计
final class RepositoryManager {
    private let lock = NSLock()
    private let queue = DispatchQueue(label: "...")
    private var cache: [String: Repository] = [:]
    // ... 100+ 行复杂逻辑
}

// ✅ 推荐：从本质出发
"""
核心需求：
1. 按路径拿到仓库 → 缓存字典
2. 线程安全 → Actor（Swift 原生支持）
3. 释放时机 → 缓存条目随 Actor 生命周期释放

最简单的正确实现优先，必要时再优化
"""
```

## 4. 问题排查流程

### 4.1 标准流程

```
1. 定义问题
   - 现象是什么？
   - 预期行为是什么？
   - 何时开始出现的？

2. 拆解假设
   - 列出所有关于这个问题的既有认知
   - 哪些是事实？哪些是假设？

3. 追问本质
   - 至少问 3 层"为什么"
   - 直到无法再分解的基本原理

4. 验证推导
   - 基于原理设计验证实验
   - 用日志/断言/单元测试确认

5. 修复方案
   - 从根源修复，而不是打补丁
   - 确保修复不引入新问题
```

### 4.2 示例

```
问题：状态查询在超大仓库上耗时数秒

1. 定义问题
   - 现象：10 万文件的仓库，status 耗时 3s+
   - 预期：应与增量信息量相关
   - 时间：rename 检测开启后开始出现

2. 拆解假设
   - 假设：文件 IO 慢 ✓ 验证
   - 假设：rename 检测是主要开销 ✓ 验证
   - 假设：工作区未做优化 ✗ 待验证

3. 追问本质
   - 为什么慢？→ 遍历工作区并逐文件比对
   - 为什么逐文件比对？→ 启用了 rename 检测
   - 为什么启用？→ 默认开启
   - 本质矛盾：检测 rename 的收益 vs 全量扫描成本

4. 验证推导
   - 对比开启/关闭 rename 检测的耗时
   - 确认 rename 检测占主要开销

5. 修复方案
   - 将 rename 检测改为可选参数，默认关闭
   - 从根源把成本控制权交给调用方
```

## 5. 代码审查检查清单

审查代码时，用第一性原理思考：

### 5.1 必要性检查

- [ ] 这段代码解决的核心问题是什么？
- [ ] 是否有更简单的实现方式？
- [ ] 是否引入了不必要的复杂性？

### 5.2 原理检查

- [ ] 实现是否符合底层原理（如 Swift 并发模型、libgit2 内存所有权）？
- [ ] 是否理解了使用的 API 的工作方式？
- [ ] 是否有未经验证的假设？

### 5.3 可维护性检查

- [ ] 代码是否表达了"为什么"而不仅仅是"做什么"？
- [ ] 注释是否解释了设计决策的原因？
- [ ] 是否便于后续基于原理进行修改？

## 6. 学习与应用

### 6.1 培养习惯

1. **多问"为什么"**：至少问 3 层，直到基本原理
2. **读源码**：理解 libgit2 与所用库的实现原理
3. **手写基础实现**：自己实现一遍关键数据结构或算法
4. **画图分析**：把抽象问题可视化（数据流、状态转换、对象生命周期）
5. **复盘总结**：解决问题后反思本质原因

### 6.2 适用场景

| 优先级 | 场景 | 建议 |
|-------|------|------|
| 🔴 高 | 核心算法、关键架构决策、内存管理 | 必须用第一性原理 |
| 🟡 中 | 性能优化、复杂 bug 排查 | 推荐用第一性原理 |
| 🟢 低 | 简单任务、重复工作 | 可以用经验/类比提效 |

### 6.3 注意事项

第一性原理虽然强大，但需要平衡效率：

```
✅ 正确用法：
- 核心技术问题 → 深入分析本质
- 关键架构决策 → 从原理推导
- 复杂 bug 排查 → 系统性分析

❌ 过度使用：
- 简单的样板代码 → 无需过度分析
- 成熟的最佳实践 → 可以直接采用
- 紧急修复 → 先解决再优化
```
